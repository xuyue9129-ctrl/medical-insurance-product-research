# 证据、状态与版本核对规则

## 字段状态
| 状态 | 含义 | 要求 |
|---|---|---|
| 原文核验 | 引文在归档原件抽取文本中逐字（exact）或高相似度（fuzzy≥0.90）找到 | 至少 1 条引文；数值应能在引文中找到 |
| 规则抽取 | 脚本按规则从原文抽出 | 研究者确认后改写为“原文核验” |
| 推定 | 基于原文的归纳、推断或换算 | 必须写 note（依据）；附引文更好 |
| 待复核 | 引文暂未找到（仅 `--allow-unverified`） | 不得进入结论；validate 报 error |
| 待核 | 未取得资料或无法确认 | 必须写 note（原因与下一步） |
| 不适用 | 产品无此项 | 建议写 note |
| 未填 | 尚未处理 | 必填字段不得为未填 |

## 引文核验怎么做
- 抽取文本按页保存在 `text/<pid>/<文件名>.txt`（`=== 第N页 ===` 分隔）。
- 比对时统一全半角、去掉所有空白与零宽字符，所以 PDF 里的断行、中英文间空格不影响匹配。
- PDF 在句中插入脚注编号（如“境内¹累计居住”抽成“境内1累计居住”）时会落到 fuzzy 匹配，需人工过目。
- 引文可用“……”连接同一页（或相邻页）的两段原文；跨页的长句会自动拼接查找。
- 写入时脚本还会检查：取值里的数字（“1.5万”“60%”“30日”）是否能在引文中找到（含“万/千/百分之”换算），找不到给 warning。
- `validate` 会对所有字段重新核验一次（文件被替换或重新抽取后仍然可靠）。

## 版本核对
- 归档时检查正文是否出现已登记的**备案条款名**（`register --clause-name`）；未登记时只能做产品名片段匹配，状态多为 unverified。
- 清单类文件（医院、药品、严重疾病）通常不含条款名，unverified 属正常，但要人工确认来自本版本的投保页/附件。
- 产品名含年份（2027）而文件只出现其他年份时给出提示：版本名年份≠文件年份是常见情况，但要确认没有拿错旧版。
- 发现文件属于其他版本（如 F款条款放进了 H款产品）时，删掉该产品目录下的文件并在 manifest 中移除，或重建工作区；不要“将就使用”。

## 可溯源产物
- `archive/.../00_manifest.json`：每个文件的来源 URL、最终 URL、获取时间、HTTP 类型、SHA256、页数、证据等级与依据、版本核对、文本缓存位置。
- `archive/.../00_资料清单.txt`：人可读清单、核心资料完整度、来源线索、版本提醒。
- `records/<pid>.json`：每个字段的值、状态、引文（文件/页码/匹配方式/相似度/证据等级/URL/文件哈希前缀）。
- Excel“证据索引”、报告“附录A”与 PPT 页脚使用同一套 E# 编号；Excel 中文件名可直接点击打开归档原件。
